# Migration history repair — the diff

2026-09-07. Written to be checkable, not believed.

## What was actually wrong

The working theory going in was three ledger entries with no file, plus version
collisions. The collisions were real. The three missing files were real. Neither
was the problem.

Production has **57 tables and none of them were created by anything in this
repository.** Every one of the ten files here was a delta against a schema that
existed only on the server. `git log --all --diff-filter=A` over
`supabase/migrations/` confirms no file creating `families`, `users`, `kids`,
`recipes` or `baby_events` has ever been committed, and none was ever deleted
either. There was no genesis to recover.

Two independent demonstrations, neither of them an argument:

```
$ npx supabase start          # replays supabase/migrations into an empty Postgres 17
ERROR: relation "public.api_usage" does not exist (SQLSTATE 42P01)
At statement: 0
ALTER TABLE public.api_usage
  ADD COLUMN IF NOT EXISTS response_preview text NULL,
```

```
$ create_branch(name: "migration-replay-proof")
status: MIGRATIONS_FAILED       # Supabase replaying main into a fresh project
public_tables: 0   ledger_rows: 0
```

Writing the three missing files would have changed nothing: they alter tables
nothing replayable creates.

## The repair

One baseline generated by `supabase db dump --schema public`, schema only —
**zero `INSERT`, zero `COPY`**, so no family data left production. The ten deltas
move to `migrations/archive/`; the CLI does not recurse, so they are never
replayed.

The dump alone was not sufficient, and the reason is worth keeping.

### pg_dump emits GRANTs and never REVOKEs

It assumes a virgin database in which no privilege exists until granted. On
Supabase that is false. `postgres` carries default privileges granting ALL on
tables, functions and sequences to `anon`, `authenticated` and `service_role`, so
every object is granted ALL the instant it is created, and the dump's narrower
`GRANT` can only add.

The first replay was therefore **more permissive than production**:

| | production | first replay |
|---|---|---|
| `authenticated` on `baby_events`, `baby_predictions`, `baby_share_links`, `deleted_items`, `memory_corrections`, `memory_decisions`, `memory_facts`, `memory_lexicon`, `reminder_log` | everything except TRUNCATE | **+ TRUNCATE** |
| `anon` on `fn_accept_invite`, `fn_skill_record_usage`, `fn_skill_get_monthly_spend` and 17 others | no EXECUTE | **+ EXECUTE** |

Two of those spend money and one accepts family invitations.

Those nine tables and twenty functions are exactly the objects created by the
migrations applied through MCP, which set grants explicitly rather than
inheriting the ambient ALL. Both databases were confirmed to have identical
`pg_default_acl` entries, so this was not an artefact of the test environment.

A restore that silently widened those permissions would have looked completely
clean: same tables, same columns, same indexes, same 198 policies. It is the same
shape as everything else fixed this week — a check that compares what it can see
and reports healthy.

The baseline now neutralises the ambient defaults before creating anything, so
the dump's explicit GRANTs are the only source of privilege. The dump's own
trailing `ALTER DEFAULT PRIVILEGES` restores the ambient defaults afterwards for
objects created later.

## The proof

Replayed twice, dumped with the same command, diffed against production.

**Local — empty Postgres 17, `supabase db reset`:**

```
$ diff -u prod_public.sql local2.sql | wc -l
0
```

**A real Supabase project — empty preview branch `zbdvgzolndxzpyhmpubc`,
`supabase db push`, migrations running as non-superuser `postgres`:**

```
$ diff -u prod_public.sql branch.sql | wc -l
0
```

Byte-identical both times. The cloud replay matters on its own: local runs as
superuser and Supabase does not, so `ALTER SCHEMA public OWNER TO
pg_database_owner`, `ALTER DEFAULT PRIVILEGES FOR ROLE postgres` and
`CREATE EXTENSION pg_trgm WITH SCHEMA public` are only really tested there.

What `--schema public` cannot see, checked separately on both:

| | production | branch |
|---|---|---|
| tables / routines / views / policies | 67 / 55 / 10 / 198 | 67 / 55 / 10 / 198 |
| `family-documents` bucket | private, 26214400, 7 mime types | identical |
| storage policies | 4 (SELECT/INSERT/UPDATE/DELETE) | identical |
| `pg_trgm` schema | `public` | `public` |

The branch was deleted afterwards. Total cost: two branches for roughly twenty
minutes at $0.01344/hour — about half a cent.

## Still outstanding: production's ledger

**Not done, and waiting on an explicit go.** The repository is now internally
consistent and proven replayable, but production's ledger still holds the old
eight rows. Until it is repaired, `npm run migrations:verify:live` will fail —
correctly, because they genuinely disagree.

This is metadata in `supabase_migrations.schema_migrations`, not a schema change.
It applies no DDL and touches no family data.

```bash
npx supabase migration repair --status reverted 20260419
npx supabase migration repair --status reverted 20260902000000
npx supabase migration repair --status reverted 20260902010000
npx supabase migration repair --status reverted 20260906000000
npx supabase migration repair --status reverted 20260906121418
npx supabase migration repair --status reverted 20260906193358
npx supabase migration repair --status reverted 20260906202607
npx supabase migration repair --status reverted 20260907025901
npx supabase migration repair --status applied  20260907150000

npm run migrations:verify:live     # should pass after the above
```

## What this does not fix

**Data.** This rebuilds an empty database with the right shape. Restoring the
family's rows is a separate problem — Supabase's own backups are the answer, and
whether they are enabled and have ever been restored from is not something this
repository can answer.

## Side effect worth knowing

Creating those preview branches **enabled branching** on the production project.
It was off before — `list_branches` returned empty at the start. Branching being
on costs nothing by itself, but if the GitHub integration is set to create a
preview branch per pull request, each one bills at $0.01344/hour. Deleting the
default `main` branch row is the documented way to turn it back off; that is a
production project setting, so it has not been touched.
